01 · Relationship model

ERPNext remains the source of truth

Relay does not duplicate Customer data. Standard Frappe Dynamic Links connect business records to Contacts; Relay adds only the communication identity, channel binding, and message history.

Business recordCustomer, Supplier, Lead, or another configured DocType.
→
Frappe ContactLinked to the business through the Contact's Dynamic Link child rows.
→
Relay identityRelay Contact + verified phone endpoint + channel-specific messages.
The business conversation is a projection, not a duplicated master.

The inbox combines messages using business_doctype and business_name, while every message still retains the exact person and endpoint involved.

03 · Core tables

Operational schema

Frappe stores these DocTypes as MariaDB/PostgreSQL tables prefixed with tab.

tabRelay Contact Type

Business inbox configuration

Enables a business DocType and selects its optional grouping field.

  • business_doctypeCustomer; also used as the document name
  • grouping_fieldTerritory, Customer Group, or custom field selected from Customer metadata
tabRelay Contact

Communication identity

One unique wrapper per Frappe Contact.

  • contactUnique Link to Contact
  • display_nameReadable conversation label
  • last_messageLatest-message cache
tabRelay Channel

Provider account

Local channel identity for the connected Hub account.

  • channelWhatsApp
  • accountHub account ID
  • enabledAvailability switch
tabRelay Contact Endpoint

Verified destination

Binds one phone number to a Relay Contact and channel.

  • endpointNormalized phone
  • verifiedAllowed for routing
  • endpoint_keyUnique SHA-256 identity
tabRelay Message

Conversation history

One immutable conversation turn with bounded status and update fields.

  • relay_contactPerson
  • channelTransport
  • business_*Owning business record
  • direction/statusLifecycle
  • message_dataTyped JSON payload
tabRelay Message Action

Durable outgoing attempt

Created before the network call so a timeout cannot cause a blind resend.

  • request_keyUnique idempotency key
  • payload_hashPrevents key reuse for different content
  • statusDispatching, Queued, Submitted, Uncertain, Rejected
  • outbound_messageConfirmed Relay Message
tabRelay Hub Event

Durable callback inbox

Stores signed inbound messages and receipt batches before projection.

  • event_keyUnique callback identity
  • payloadOriginal bounded callback
  • projection_statusPending, Projected, Uncategorized, Ignored, Failed

Per-user business view

Stores last-read and restored chat position.

tabRelay Message Read

Exact read evidence

Unique user-message pairs power the read-by bubbles.

tabRelay Conversation Summary

AI summary result

Tracks background summary status, source messages, input hash, and structured result.

04 · Incoming message flow

Persist first, process second

Hub sends a signed batch

Core validates the account, timestamp, HMAC signature, payload size, and a maximum of 50 events.

Core inserts Relay Hub Event

The unique event key makes repeated webhook deliveries safe.

The HTTP request is acknowledged

Provider processing does not hold the webhook request open.

A background worker projects the event

It resolves one enabled channel and one verified endpoint.

Relay Message is inserted

The before-insert hook associates the business automatically only when the contact has one unambiguous configured business.

Socket.IO publishes the change

Permitted users refresh the visible timeline without browser polling.

05 · Outgoing and delivery flow

Idempotent sends and batched receipts

Outgoing message

The selected business and contact are permission checked. Core creates a Message Action, commits it, calls Hub, and creates the outgoing Message only after a confirmed provider ID.

Dispatching→Queued→SubmittedUncertain / Rejected

Delivery receipts

Hub may push up to 500 compact statuses in one signed callback. Core applies monotonic transitions and emits one realtime refresh for the affected conversation.

Sent→Delivered→ReadFailed
WhatsApp's customer-service window is derived locally.

The most recent non-legacy incoming message opens the 24-hour reply window. Outside it, Relay requires an approved template.

07 · Permissions and responsibility

Every layer is checked server-side

Business permission

The user must be able to read the Customer or configured business document.

Contact permission

The linked Frappe Contact and Relay Contact must also be readable.

Responsibility

A group claim, direct assignment, or team membership determines who handles the conversation.

Filtering happens before pagination

Frappe permission query conditions combine assignment and business ownership in SQL. A group claim never grants access to a business record the user could not already read.

08 · Current implementation boundaries

Known schema decisions to address before very large production loads

01
Relay uses the standard Frappe Contact model.

Business records are resolved through Contact Dynamic Links, so no separate contact DocType setting is required.

02
One phone linked to several businesses is inherently ambiguous on inbound traffic.

Relay does not guess. An ambiguous inbound message remains unassigned rather than appearing under the wrong business. Outgoing messages from the business inbox always carry the selected business explicitly.

03
Business timelines need a dedicated composite index at multi-million scale.

Current indexes cover contact, channel, and conversation history. Add a composite index around business DocType, business name, channel, and message ordering before very large production volumes.
